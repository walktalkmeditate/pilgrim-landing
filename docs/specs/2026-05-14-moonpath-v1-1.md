## Problem

**Problem:** /moonpath v1 is a vertical stack of 8 widgets read at one instant (`now`). The page lacks a way to scrub time, a connective tonal layer between widgets, and two genuinely-loved almanac dimensions: eclipses + moonrise direction. The page also keeps a year-only standstill slider that is structurally a date-scrubber-in-disguise; one unified time control is simpler.

**Who feels it:** Visitors who already arrived at /moonpath (so they care) and want to (a) re-read the page for a past or future moment, (b) understand the tonal "why this matters", or (c) plan around eclipses + moonrise compass bearings.

**When:** Every page-load. The "now-only" view is workable but flat — most almanacs allow scrubbing through time.

**Today's workaround:** Year slider on the standstill widget gives partial time-travel (year-only) for one widget. The other 7 v1 widgets ignore it. Users wanting "next eclipse" or "where does the moon rise from my house" check external tools.

**Cost of doing nothing:** Page reads as a static read-out, not a contemplative instrument. /moonpath sits stylistically below /sunpath (which has interactive analemma + turnings tabs) on the depth axis. Eclipse + azimuth are the two missing dimensions every long-form almanac includes; their absence is felt by the kind of user who'd subscribe to an ICS feed.

---

## In scope

- **F1 — Page-level date scrubber.** One horizontal control at the top of the widget stack. Drag/keyboard to any instant in `[currentYear − 5000, currentYear + 5000]`. All **7 v1 widget renders** (dome arc, phase clock, earthshine annotation, apparent-size dial, lux ring, standstill annotation, tide curve) + the **2 new widgets** (eclipse pointer, moonrise azimuth dial) = **9 widget renders total** re-render against the scrubbed instant. The year-only standstill slider from v1 is **removed** — its control surface is replaced by the page-level scrubber (so v1's "8 sections including the slider chrome" → v1.1's "9 widget sections" is a `−1 slider + 2 widgets = +1 section` change, plus the new scrubber chrome sitting above the widget stack).
- **F2 — Interstitial coord-aware prose.** One italic sentence between adjacent widget sections — **8 interstitials total** for 9 widget sections after v1.1 lands. (The "entry block" — page heading + lede + coord-entry form, defined formally below — sits above the first widget and has no preceding interstitial.) Each generated by a pure `interstitialFor(output, sectionId)` function from a fixed lookup table keyed on `sectionId` first then a small state tuple per slot (e.g., "Tonight at your latitude the moon never sets — circumpolar.").
- **F3 — Eclipse pointer widget.** Two text lines: next solar eclipse + next lunar eclipse visible from the scrubbed coord/date. Uses Meeus Ch. 54 (solar) + Ch. 54 lunar shadow geometry. No SVG dome rendering of the eclipse path itself — just a date, magnitude, and one prose line. Restraint over spectacle.
- **F4 — Moonrise azimuth dial.** Small SVG compass-rose with a single needle showing tonight's moonrise bearing (degrees east of north) at the user's coord. Cardinal labels N/E/S/W. Annotation line: *"Moon rises at <bearing> tonight — look toward <cardinal-prose>."*

## Non-goals

- **Eclipse map / shadow path.** No D3-based map rendering, no globe overlay. Date + magnitude + one prose line only. If a user wants the path map, NASA hosts it.
- **Two-coord overlay.** Compare-two-coords (the wild #2 dream) explicitly deferred to v2.
- **Date scrubber URL persistence.** Scrubbing does NOT update `?date=` on every drag (too noisy). Initial load reads `?date=` once (per AC #3); subsequent scrubs are in-memory only. Manual share via URL params still works as in v1.
- **Audio.** No Web Audio tide clock; spec round explicitly dismissed.
- **Memory ribbon (18-month strip).** Deferred to v1.2.
- **Libration map.** Deferred to v1.2 or v2; too big.
- **New tide ports.** The 8 deferred ports remain deferred — separate licensing work.

## Decisions (D24–D30)

- **D24 — One scrubber, full range, integer-tick log scale.** Subsumes the v1 year-only standstill slider. Slider `value` is an integer index `i ∈ [−500, +500]` (1001 ticks). Mapping to `daysFromNow`:
  ```
  daysFromNow(i) = sign(i) * (1.0293 ** |i| − 1)
  ```
  Base **1.0293** chosen so `|i|=500` reaches `~1.83 × 10⁶` days = `5000 × 365.25` exactly: `ln(5000 × 365.25) / 500 ≈ 0.02884 ⇒ base ≈ exp(0.02884) ≈ 1.02926`, rounded to 1.0293. Verified: `1.0293^500 ≈ 1.88 × 10⁶ days ≈ 5,150 yr` (slightly over the ±5,000 yr target; spec gates rely on `min(...)` clamps in implementer code if exact bound matters). Ticks near `i=0` are sub-daily (`i=1 → 0.0293 days ≈ 42 min`); ticks near `|i|=500` are multi-year. Monotonic, no clamp required inside `scrubberValueToInstant(i, nowMs)`. **Rounding:** the function output `daysFromNow(i)` is multiplied by `86_400_000` to get a millisecond delta, then rounded to the nearest integer millisecond. `i=0` returns exactly `nowMs` (no rounding drift at center).
- **D25 — Interstitial prose lookup is a static table keyed by `sectionId` first, then state.** Each of the 8 interstitial slots has its own micro-table keyed on a small state tuple relevant to that slot. The 4-tuple `(isCircumpolar, isMoonBelowHorizon, springNeapState, k_bucket)` is the **superset**; individual slots use only the 1-2 dimensions that matter for them (e.g., the interstitial *above the lux ring* keys only on `k_bucket`; the interstitial *between standstill and tide* keys only on `springNeapState`). **Curated cell target: 24–32 cells across the 8 slots, minimum 2 cells per slot** (AC #7 enforces). Default for any unmapped cell returns `''` (empty string — NOT em-dash) → renderer adds `hidden` attribute to the `<p>` element. Sentences live in `js/moonpath.js` as `INTERSTITIAL_TABLE` const (an object of `{sectionId → {stateKey → prose}}`).
- **D26 — Eclipse math: Meeus Ch. 54 low-precision.** Two helpers, both coord-aware:
  - `nextSolarEclipseAfter(date, lat, lon)` — lat/lon-in-eclipse-band filter (penumbra-coarse). Returns `{utcMs, magnitudePct}` where `magnitudePct` is the **Meeus-style linear magnitude** (fraction of the solar disk's *diameter* obscured at maximum, 0–100). Spec note: linear magnitude is what Meeus Ch. 54 yields directly; converting to area would require `1 − (1 − m)² ` adjustments that aren't load-bearing for an almanac annotation. Text rendering uses the word "magnitude" so users see what astronomy textbooks would.
  - `nextLunarEclipseAfter(date, lat, lon)` — visibility requires *any portion* of the eclipse window to overlap with `moon above horizon at (lat, lon)`. A 2-hour partial eclipse counts even if the moon sets midway. (NOT only mid-eclipse.) Returns `{utcMs, kind}` where `kind ∈ {'total', 'partial', 'penumbral'}`. Resolves Q-Lunar-Eclipse-Visibility.
  Accuracy envelope: **±1 day, ±5 pct-points magnitude** (absolute, e.g., a true 25% magnitude event passes if predicted in [20%, 30%]). Sufficient for almanac use, not for safe direct viewing — annotation says so. Eclipse fixtures in `sunpath-math.test.js` deliberately exclude grazing events (true magnitude <5% or >95%) where the tolerance straddles zero/total visibility.
- **D27 — Eclipse text format + scrub-range fallback.** Two lines:
  - *"Next solar eclipse from this coord: 2026-08-12, magnitude 24%."*
  - *"Next lunar eclipse from this coord: 2026-09-25, total."*
  When `|scrubYear − currentYear| > 3000` (strict: year ±3000 inclusive still renders, year ±3001 fallback), the eclipse pointer renders a single fallback line: *"Eclipse predictions unavailable beyond ±3,000 yr — Meeus low-precision envelope."* (Range deliberately tighter than the scrubber's ±5,000 yr; standstill annotation, phase, lux, and azimuth continue working further out under their own accuracy footnotes.) Implementer pins the bound as a constant `ECLIPSE_VALID_YR_RANGE = 3000` so AC #8 fixtures + the fallback test are both rooted to one number.
- **D28 — Moonrise azimuth = compass bearing, domain `[0°, 360°)` measured clockwise from N.** `moonriseAzimuthAt` always returns a value in this half-open range (or `null` for circumpolar — see below). Accuracy envelope: ±3° vs almanac reference. Dial SVG is 120 × 120 px to match other small widgets. **Circumpolar handling:** when the moon does not rise at the user's coord on the scrubbed date (e.g., high-latitude winter), `moonriseAzimuthAt` returns `null`; the dial renders dimmed (50% opacity) with no needle, and the annotation line reads *"Moon does not rise tonight — circumpolar."* Cardinal label prose mapping (8 buckets, half-open closed-left/open-right matching v1 D23 spirit; the due-north bucket explicitly wraps around 360° → 0°):
  - `[337.5°, 360°) ∪ [0°, 22.5°)` → "due north"
  - `[22.5°, 67.5°)` → "northeast"
  - `[67.5°, 112.5°)` → "due east"
  - `[112.5°, 157.5°)` → "southeast"
  - `[157.5°, 202.5°)` → "due south"
  - `[202.5°, 247.5°)` → "southwest"
  - `[247.5°, 292.5°)` → "due west"
  - `[292.5°, 337.5°)` → "northwest"
- **D29 — Scrubber range = same as v1 standstill slider (±5,000 yr).** Inherits v1's D20 two-tier accuracy footnote — now applies to ALL widgets, not just standstill. Footnote moves from below the slider to a single page-level note above the scrubber.
- **D30 — Scrub-time tide-window fallback.** Tide bake window is **±30 calendar days inclusive** of `nowMs` — `|scrubbedInstant − nowMs| ≤ 30 × 86400000 ms` shows the curve; outside that range shows the fallback line: *"Tide curve unavailable beyond the bake window — try a date within ±30 days."* Boundary is closed (30 days exactly still renders the curve). Inland-coord behavior unchanged (v1 D9: inland coords already hide the tide section when nearest baked port >200 km). Other widgets (phase, lux, azimuth, eclipse) work across the full ±5,000 yr range with their own accuracy envelopes (D27 caps eclipse at ±3,000 yr).

## Acceptance criteria

**Widget section order (v1.1).** Reading top to bottom, the 9 widget sections appear in this order: (1) moon-in-sky dome, (2) moonrise azimuth dial, (3) phase clock, (4) earthshine annotation, (5) apparent-size dial, (6) lux ring, (7) eclipse pointer, (8) standstill annotation, (9) tide section. Interstitials sit between every adjacent pair → 8 total. **AC #8 and AC #10 use this order to derive the new widgets' adjacency claims.**

1. [ ] **Scrubber present.** `<input type="range" id="mp-date-scrubber">` exists at the top of the widget stack on `/moonpath/`. No two scrubbers visible — old standstill year-slider element is removed.
2. [ ] **Scrubbing recomputes all widgets.** Dragging the scrubber updates all **9 widget renders**: dome arc, phase clock, earthshine annotation, apparent-size dial, lux ring, standstill annotation, tide curve (or D30 fallback), eclipse pointer, moonrise azimuth dial. All in one `recompute(state)` call.
3. [ ] **Scrubber default = URL `?date=` if present, else `now`.** First page-load reads `parseParams(location.search).date`; if a valid ISO date is present, the scrubber initializes to that instant. Otherwise it defaults to `now`. Resetting (double-tap or keyboard Home) always returns to `now` regardless of URL.
4. [ ] **Scrubber accessibility + keyboard.** `aria-label="Scrub date"`, `aria-valuetext` updates with the human-readable scrubbed date. Keyboard bindings: Left/Right arrow = ±1 tick; Shift+Left/Right = ±10 ticks; Home = reset to `now` (`i=0`); End = no special binding (default `<input type=range>` behavior — jumps to max value, which the implementer may leave default since reaching `i=+500` directly is harmless). PageUp/PageDown not bound. (Note: ticks are non-linear by D24 — a 1-tick step at `i=0` is ~42 min, a 1-tick step at `|i|=400` is ~1 year. This is intentional; users wanting a precise date use the URL `?date=` param.)
5. [ ] **Interstitial DOM elements present, content optionally hidden.** Exactly **8 `<p class="mp-interstitial">` elements** exist in the rendered page DOM — one between each adjacent pair of the 9 widget sections. The entry block has no interstitial. When `interstitialFor(output, sectionId)` returns an empty string, the element receives the `hidden` attribute (still in DOM, not visible). Assertion: `document.querySelectorAll('p.mp-interstitial').length === 8`.
6. [ ] **All interstitials recompute on scrub.** Every `recompute(state)` triggers a render pass that updates every interstitial — not just the one adjacent to the widget being scrubbed. No stale text after a scrub.
7. [ ] **Curated interstitial-prose set.** `INTERSTITIAL_TABLE` in `js/moonpath.js` contains **24–32 curated strings total** across the 8 per-section sub-tables (per D25). A test asserts: (a) total count is within `[24, 32]`; (b) **every sub-table has ≥2 entries** (no slot is empty); (c) every entry is a non-empty string; (d) no entry contains `<` or `>`; (e) no entry contains the word `"supermoon"` (the v1 D6 banned word — restated here so this AC reads standalone).
8. [ ] **Eclipse pointer renders in pinned slot.** Two-line pointer between the **lux ring** (slot 6, above) and the **standstill annotation** (slot 8, below) — slot 7 in the order above. Lines as per D27. Out-of-range fallback (|`new Date(scrubbedInstant).getFullYear()` − currentYear| > 3000) renders the single D27 fallback line.
9. [ ] **Eclipse helper functions exported.** `SunPathMath.nextSolarEclipseAfter(date, lat, lon)` and `SunPathMath.nextLunarEclipseAfter(date, lat, lon)` exported with stable signatures (both coord-aware per D26). Each has ≥3 historical fixtures in `js/sunpath-math.test.js` matching USNO predictions within D26's tolerance (±1 day, ±5 pct-points Meeus linear magnitude). Fixtures deliberately exclude grazing events (true magnitude <5% or >95%) per D26.
10. [ ] **Moonrise azimuth dial renders in pinned slot.** Compass-rose SVG between the **moon-in-sky dome** (slot 1, above) and the **phase clock** (slot 3, below) — slot 2 in the order above. Single needle, labels N/E/S/W, annotation line below the dial.
11. [ ] **Azimuth math exported.** `SunPathMath.moonriseAzimuthAt(date, lat, lon)` exported, ≥3 fixtures matching almanac (timeanddate.com or USNO) within the D28 accuracy envelope (±3°).
12. [ ] **D28 cardinal lookup table is deterministic.** `cardinalProseFor(bearingDeg)` returns exactly one of 8 strings; boundary values at 22.5, 67.5, 112.5, 157.5, 202.5, 247.5, 292.5, 337.5 land in the upper bucket; the due-north bucket explicitly wraps `[337.5, 360) ∪ [0, 22.5)`. Implemented as a hand-rolled boundary loop in `js/moonpath.test.js` — **no `fast-check` or other property-test dep** (v1 AC #18 zero-dep gate).
13. [ ] **Date scrubber out-of-band tide fallback + boundary fixture.** Scrub to date 90 days in the future → tide section shows D30 fallback line. Scrub back to within 30 days → curve returns. Boundary fixture in `js/moonpath.test.js`: a `recompute` call with `now + 30 × 86_400_000` ms returns a curve (not fallback); a call with `now + 30 × 86_400_000 + 1` ms returns fallback.
14. [ ] **Two-tier accuracy footnote moved to page-level.** Sits above the scrubber, single instance. Standstill widget no longer has its own footnote.
15. [ ] **v1 AC #6 supermoon grep gate still clean.** Eclipse + azimuth additions don't introduce the word.
16. [ ] **v1 AC #18 no-deps gate still clean.** Zero npm deps, no `package.json`.
17. [ ] **v1 AC #17 no-third-party-hosts gate still clean.** No new external origins.
18. [ ] **All v1 test suites green.** sunpath-math, daylight-math, daylight-perf, tide-math, moonpath. No regressions. New suite additions: ≥3 fixtures × 3 new helpers + interstitial table-shape tests + cardinal-bucket boundary tests.
19. [ ] **Scrubber renders via rAF-throttled pipeline.** Pointer/keyboard events on the scrubber are coalesced via `requestAnimationFrame`: at most one `recompute(state)` + render pass per animation frame regardless of input event rate. **Programmatic test:** `js/moonpath.test.js` installs a stub `requestAnimationFrame` that fires its callback exactly **5 times** during the test, fires **100 synthetic `input` events** on the scrubber across that interval, and asserts both: (a) `recomputeCount === 5` (one per rAF tick — exact, not ≤; catches a "never coalesces" bug where count=100, AND a "never fires" bug where count=0); (b) the last recompute is called with the latest input value (verifies trailing edge fires, not just leading).

## Open questions

- **Q-Scrubber-Granularity.** *Resolved inline in D24:* center ticks are sub-daily (`i=1 → ~42 min`), edge ticks are multi-year. The slider is a log scrubber, not a calendar widget; users wanting day-precision use the URL `?date=` param. UI label below the scrubber shows the date in human-readable form (e.g., "Sat 14 May 2026, 14:32 UTC").
- **Q-Eclipse-Past (non-blocking).** Should the eclipse pointer ALSO show the most-recent PAST eclipse alongside the next future one? Adds nostalgia/memory dimension. Spec defaults to "next only" for simplicity; can add in follow-up if user requests.
- **Q-Lunar-Eclipse-Visibility.** *Resolved inline into D26 above:* "any portion of eclipse coincides with moon above horizon" filter (more accurate than mid-eclipse-only). No longer blocking.
- **Q-Moonrise-When-No-Rise (non-blocking).** Circumpolar nights: moon may not rise that day. What does the azimuth dial show? Default: dial dimmed + annotation line reads *"Moon does not rise tonight — circumpolar."* Same prose path used for interstitial circumpolar state.

## Risks

- **Eclipse math accuracy creep.** Meeus Ch. 54 is "low-precision" by Meeus's own framing. ±1 day error means an eclipse can shift from 2026-08-12 to 2026-08-13 in our prediction. Almanac caveat in the eclipse pointer prose mitigates this — *"Predictions are reference-only; consult NASA Eclipses for definitive paths and safety."*
- **Scrubber UX precedent.** Range inputs with logarithmic transforms behave non-linearly to mouse drag, which can confuse new users. Mitigation: above-scrubber prose explains scale ("drag near edges for centuries, near center for days").
- **Interstitial prose tonal drift.** With 80 possible cells and 24–32 curated strings, most cells fall back to empty. Some curated combinations may read awkwardly; AC #7 enforces a count + shape-check, but tonal judgment is still human. Default cell returns `''` (empty string per D25) → renderer adds `hidden` attribute so a bad cell never ships.
- **Recompute perf on scrub.** All 9 widgets recomputing at every pointer/keyboard event = potential lag. Mitigation: rAF-throttle (one recompute+render per frame max), enforced as a code-shape gate by AC #19. If a future regression makes a single recompute exceed one frame, treat it as a follow-up bug, not a v1.1 blocker.
- **Page density.** Adding 2 widgets + 8 interstitials + 1 scrubber on top of v1's already-dense page. Mitigation: scrubber subsumes year-slider (net +0 chrome on the time-control surface); interstitial prose is single-line italic. The honest dream note ("almanacs gain value from stability") applies — if v1.1 still feels too dense after build, accept that as feedback for v1.2 trims, not as a v1.1 blocker.

## Entry block (term definition)

The "entry block" referenced in AC #5 and elsewhere is the section above the first widget: page heading + lede prose + locate button + manual lat/lon inputs. No interstitial appears between the entry block and the first widget (dome arc).
